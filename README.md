# boatai — 경정 예측 (개인 참고용)

미사리 경정 경주를 공공데이터포털 오픈API 로 모아 승률을 예측하고, **예측을
발주 전에 확정 저장한 뒤** 실제 결과·배당과 대조해 적중률과 회수율을 낸다.
경마 버전(`~/dev/horseai`)의 구조를 따르되, 경정의 성질에 맞춰 바꿨다.

## 먼저 — 왜 `NO_OPENAPI_SERVICE_ERROR` 가 났나

키 문제가 아니었다. **호출 경로와 파라미터 규칙이 마사회 API 와 다르다.**

| | 한국마사회 (horseai) | 경정 (boatai) |
|---|---|---|
| 경로 | `/B551015/API26_2/entrySheet_2` | `/B551014/`**`<서비스명>`**`/<오퍼레이션명>` |
| 응답 형식 | `_type=json` (생략 가능) | **`resultType=json` (필수)** |
| 페이지 | 생략 가능 | `pageNo`·`numOfRows` **필수** |
| 미승인 | 결과코드 `20` | **HTTP 403** |

경정은 호스트에 서비스 세그먼트가 들어간다. 짧은 경로로 부르면 게이트웨이가
서비스를 못 찾아 코드 12(`NO_OPENAPI_SERVICE_ERROR`)를 돌려준다. 경로는
포털 데이터셋 페이지에 임베드된 Swagger 명세에서 그대로 받아
`config/openapi/*.json` 에 보관했고, 레지스트리(`kboat/endpoints.py`)는 그
값을 쓴다 — 추측한 경로가 하나도 없다.

또 하나의 함정: **`race_no` 는 2자리 0채움 문자열이어야 한다.** `"1"` 을 주면
오류 없이 0건이 온다. 가장 찾기 어려운 종류의 실패라 파라미터를 만드는 한
곳(`to_api_params`)에서 강제한다.

### 승인 현황 (2026-08-13 실측)

승인된 6개 — 이것만으로 파이프라인이 완결된다.

| API | 쓰임 |
|---|---|
| 출주표 | **피처 전부** (선수·모터·보트·코스별 성적, 42필드) |
| 경주결과순위 | **착순 레이블 + 실제 경주일자** (2002~, 19만 행) |
| 경주결과 | 승식 배당 + 1~3착 (연 단위 일괄) |
| 배당률 | 경주 단위 확정배당 (결손 보충용) |
| 선수 회차별 성적 | 선수 폼 스냅샷 |
| 선수 다승순위 | 신인·복귀 선수의 사전값 |

미승인 13개는 `python -m boatai.kboat.probe` 가 403 으로 구분해 보여준다.
그중 **틸트각 정보**(경주별 조정각 — 선수가 그 경주를 어떻게 타려는지 드러나는
설정값)는 공개 자료 중 작전에 가장 가까워, 추가 신청할 가치가 가장 크다.

## 쓰는 법

```bash
python -m boatai.kboat.probe                 # 승인·경로·응답필드 확인
python -m boatai.kboat.collect backfill      # 2002~올해 (약 700회 호출)
python -m boatai.kboat.collect daily         # 매일: 올해분 갱신
python -m boatai.model train                 # 학습 + 워크포워드 검증
python -m boatai.predict upcoming            # 발주 전 경주의 예상 확정 저장
python -m boatai.verify                      # 실전 기록 검증
python -m boatai.audit --days 30 --strict    # 자료 결손 점검
python -m boatai.site                        # dist/ 로 정적 사이트 빌드
```

경주일(수·목) 흐름은 `daily` → `predict upcoming` → `site` →
(경주 후) `daily` → `verify` → `audit` → `site` 순이다.

### 사이트

```bash
python -m boatai.site --db data/boatai.sqlite --out dist
python -m http.server 8000 -d dist    # http://localhost:8000
```

`dist/` 에 정적 HTML 만 나온다. 개인용이라 광고·애널리틱스·검색엔진 태그·
사이트맵은 두지 않았다 — `config.yaml` 의 `site.url` 을 채우면 canonical 만 붙는다.

| 페이지 | 내용 |
|---|---|
| `/` | 다가올 경주(1순위·기호·승률), 최근 결과, 검증 요약 |
| `/race/<경주키>/` | **상세예상지** — 예상판, 1턴마크 전개 시뮬레이션, 체크포인트, 출주표, 최근 8경주, 확정배당 |
| `/day/<YYYYMMDD>/` | 그날 전 경주 |
| `/results/` | 결과 아카이브 (빗나간 예상 포함) |
| `/accuracy/` | 승식별 적중률·회수율, 코스별·월별 |
| `/strategy/` | 베팅금 규칙(마틴게일 등)과 선택 규칙 시뮬레이션 |

화면이 지키는 것:

* **공개 / 검증 배지** — 발주 전에 확정 저장한 `v1` 과 시간순 교차검증 `v1-oos` 를
  배지로 구분한다. 표에서 섞이면 며칠 뒤의 나는 둘을 같은 것으로 읽는다.
* **회수율을 적중률 옆에 둔다** — 승식 조합을 보여주는 칸 바로 위에
  '이 방식들의 장기 회수율은 모두 100% 미만'을 적는다.
* **정번은 색 배경 + 큰 숫자** — 실제 艇 색(1 백 · 2 흑 · 3 적 · 4 청 · 5 황 ·
  6 녹)을 배경으로 쓰고 숫자를 그대로 크게 적는다. 처음엔 보트 모양 SVG 위에
  숫자를 얹었는데, 선체가 좁고 어두운 정번(2·4·6)에서 숫자가 묻혀 읽히지
  않았다. 표에서 필요한 것은 장식이 아니라 식별이다. 보트 그림은 주행 재생
  화면에만 남겼다 — 거기서는 크기와 각도가 정보를 담는다.
* **경주는 항상 1R 부터** — 하루 안의 순서는 시행 순서이고, 그것이 사람이
  경주를 찾는 순서다. 날짜만 최신이 위로 온다.
* **표본 수를 함께 적는다** — 코스 연대율 옆의 '3회' 는 그 백분율을 믿지 말라는
  뜻이다.

## 배포 (GitHub Pages · 프로젝트 페이지)

`.github/workflows/publish.yml` 이 개최일마다 자동으로 수집 → 예상 → 빌드 →
배포까지 한다. 처음 한 번만 아래를 해 두면 된다.

1. **저장소 Secrets** 에 `KBOAT_SERVICE_KEY` 추가 (공공데이터포털 인증키)
2. **Settings → Pages → Source** 를 `GitHub Actions` 로
3. 워크플로를 한 번 손으로 실행(`workflow_dispatch`)

### 경로 — 이것만 틀리면 전부 404

프로젝트 페이지는 `user.github.io/<저장소>/` 아래에 놓이므로 내부 링크가 모두
그 경로로 시작해야 한다. 워크플로가 `BOATAI_BASE=/<저장소명>` 을 넣어 빌드하고,
템플릿은 `{{ base }}` 를 앞에 붙인다. 로컬에서는 비워 두고 굽는다.

```bash
python -m boatai.site                     # 로컬 (루트)
BOATAI_BASE=/boatai python -m boatai.site # 배포와 같은 조건으로 확인
```

**함정 하나** — Jinja 매크로는 `{% from %}` 로 불러오면 상위 컨텍스트를 못 받는다.
`with context` 를 빠뜨리면 `{{ base }}` 가 조용히 빈 문자열이 되어 링크가 전부
루트로 나가고, 로컬에서는 멀쩡히 동작하므로 배포 후에야 드러난다.

### 언제 도는가

| 크론(UTC) | KST | 하는 일 |
|---|---|---|
| `0 0 * * 3,4` | 수·목 09:00 | 출주표 수집 → **발주 전** 예상 게시 |
| `30 13 * * 3,4` | 수·목 22:30 | 착순·배당 수집 → 적중률 반영 |

저녁에 한 번만 도는 이유: 착순은 경주마다 들어오지만 배당은 그날 늦게 한 번에
들어온다. 낮에 여러 번 돌리면 '착순은 있는데 적중은 모름' 인 화면이 오래 남는다.

### 수집 자료는 캐시로 나른다

DB 는 137MB(raw_json 정리 후)라 저장소에 담지 않고 `actions/cache` 로 옮긴다.
캐시가 없으면(첫 실행·만료) 24년치를 처음부터 받는다 — 700회 남짓이라 일일
한도 안에 들어가지만 시간은 걸린다. 모델(`models/model.joblib`, 4.3MB)은
저장소에 두어 CI 가 재학습 없이 그대로 쓴다.

## 경정이라서 다른 점

* **출주 정수가 항상 6이고 정번이 곧 코스다.** 경마처럼 두수가 흔들리지 않아
  경주 간 비교가 쉽고, 대신 코스(1~6)가 압도적인 단일 피처다.
* **모터가 회차마다 추첨으로 배정된다.** 장비 운이 결과를 크게 가르므로 모터
  성적은 선수 기량만큼 중요한 축이다.
* **출주표가 이미 롤링 지표를 준다.** 최근 6회차 성적, 코스별 6개월 연대율,
  모터·보트 연대율이 전부 경주 전 공개값이다. 과거 결과에서 다시 계산하지
  않으므로 **누수 위험도 없다**.
* **발주 전 배당률이 없다.** 단승 배당은 적중 조합의 것만, 경주 후에 공개된다.
  그래서 경마 버전의 '1인기 베이스라인'을 쓸 수 없고, 대신 **1코스 고정**과
  **최근 폼 최고**를 베이스라인으로 둔다.
* **삼쌍승·쌍복승은 배당 자료가 없다.** 판정에서 아예 뺀다 — 적중만 세고
  회수율을 못 내면 표의 절반만 참이 되는데, 어느 절반인지 보는 사람은 모른다.

| 지표 | AI 모델 | 1코스 고정 | 최근폼 최고 |
|---|---|---|---|
| 단승 적중률 | **47.8%** | 36.8% | 29.0% |
| 단승 회수율 | 86.4% | 85.0% | — |

로그손실 0.362 · AUC 0.808 · 배당 커버리지 100%

승식별 회수율(사후 워크포워드 기준): 단승 86.4% · 연승 89.7% · 쌍승 73.0% ·
복승 73.7% · 삼복승 76.4% · **다섯 승식 통합 79.8%**.

**중요 — 맞히는 것과 버는 것은 다르다.** 모델은 1코스 고정을 11%p 앞서지만,
회수율은 어느 승식에서도 100% 를 넘지 못한다. 경정의 공제율(약 20~27%)을
이기지 못한다는 뜻이다. 이 수치는 숨기지 않고 그대로 표에 남긴다 — 적중률만
크게 적고 회수율을 빼면 스스로를 속이게 된다.

## 전개 시뮬레이션 — 1턴마크 물리

`src/boatai/simulate.py`. 경정은 **한 지점에서 승부가 갈리는 종목**이다. 여섯
척이 같은 1턴마크로 몰리고, 거기서 안쪽을 잡느냐 바깥으로 도느냐가 나머지 두
바퀴 반을 결정한다. 그 한 지점을 실제로 돌려 본다.

핵심은 **선회반경–속도 상충** 하나다. 반경 r 로 도는 배는 옆으로 밀리지 않을
만큼만 속도를 낼 수 있다:

```
v(r) = √(A·r)          t(r) = π·r / v(r) = π·√(r/A)
```

반경이 커지면 **통과 시간은 늘지만 빠져나오는 속도는 빨라진다.** 인빠지기와
휘감기가 갈리는 이유가 이 한 줄이다.

### 보정 — 물리가 실제로 일을 하는지 확인한다

상수(선회 간격, 탈출 속도 환산, 라인 탈취 시간, 기량 변동)는 실측 자료가 없어
**코스별 1착 비율로 맞췄다**. 중요한 건 보정을 **'여섯 척의 기량을 완전히 같게
둔 상태'**에서 한다는 점이다. 실제 경주로 맞추면 모델 확률이 이미 코스 우위를
담고 있어, 물리가 엉망이어도 총합은 맞는 것처럼 보인다.

| 코스 | 1 | 2 | 3 | 4 | 5 | 6 | 오차 |
|---|---|---|---|---|---|---|---|
| 실측 | 36.1 | 23.2 | 16.2 | 12.5 | 7.8 | 4.1 | |
| 현재 (순수 기하학) | 36.2 | 22.3 | 16.2 | 11.8 | 7.9 | 5.5 | **0.033** |
| 이전 | 21.0 | 18.8 | 16.3 | 16.6 | 14.9 | 12.5 | 0.399 |

처음엔 실제 경주로 맞춰 오차 0.041 을 얻고 끝냈다가, 기량을 같게 두고 돌려 보고서야
**물리가 거의 아무 일도 안 하고 있었다**는 걸 알았다. 원인은 둘이었다.

* `PACE_SIGMA` 6.5% 가 90초 주행에 곱해져 5.8초를 흔들었다 — 1턴마크에서 번
  0.55초를 통째로 덮었다. 실제 속도 변동에 가까운 2% 로 낮췄다.
* 안쪽 라인을 '먼저 도착한 배'가 가져가게 했더니 정번이 무의미해졌다. 실제로는
  **안쪽에서 출발한 배가 기본으로 가지고**, 바깥 배가 뺏으려면 한 칸당 `TAU`
  만큼의 시간 우위가 필요하다.

또 하나 — 모델 확률을 그대로 앵커로 쓰면 **코스 효과가 이중 계산**된다(1코스가
44.7%까지 부푼다). 그래서 앵커에서 **모델이 코스에 부여한 몫을 나눠** 기량만
남긴다. 이 과정에서 모델이 가운데로 수축한다는 것도 드러났다(1코스를 3.5%p
낮게, 6코스를 1.9%p 높게 본다).

### 코스 — 트랙이 아니라 열린 수면이다

처음엔 경마장처럼 **폐곡선 트랙**으로 그렸는데, 실제 경정장 사진을 보고 틀렸다는
걸 알았다. 경정장은 주로가 없다. **열린 수면에 턴마크 부표 두 개(300m 간격)가
떠 있고**, 그 사이를 센터폰툰이 가를 뿐이다. 배는 어디로든 갈 수 있고 다만 두
부표를 돌아야 한다 — 안쪽을 얼마나 좁게 감느냐가 전적으로 선수의 선택이고,
그것이 곧 전법이다.

이 차이가 물리에도 영향을 준다. 트랙 모델에서는 선회 반경을 38m 로 뒀는데,
실제로는 부표를 20m 안팎으로 감아 돈다 — 선회 속도가 43km/h 로 떨어지고
안팎 격차가 훨씬 커진다.

| | 트랙 모델(틀림) | 부표 모델(실제) |
|---|---|---|
| 최내측 반경 | 38m | **20m** |
| 최내측 선회속도 | 47km/h | **43km/h** |
| 최내측 슬립각 | 25.9° | **23.0°** |
| 최외측 선회속도 | 53km/h | **56km/h** |
| 공식 거리 | 1800m | 1800m |
| 실제 주행 | 1800m | **2,177m** |

공식 1주회 600m 는 부표를 스치듯 도는 이론선이다. 실제로는 선회 반경만큼 더
돌아 3바퀴에 약 2,180m 를 달리며, 완주 110초로 실제 경정(1분 50초 안팎)과 맞는다.
둘을 섞으면 완주 시간이 20% 짧게 나온다 — 테스트가 이 혼동을 막는다.

### 주행 재생 — 드리프트가 핵심이다

상세예상지에서 **경주를 실제로 돌려 볼 수 있다**([static/race-player.js](static/race-player.js)).
말은 다리로 방향을 바꾸지만 **배는 못 바꾼다.** 직선에서 싣고 온 속도를 선회
속도까지 깎아내면서 동시에 방향을 틀어야 하고, 그 둘을 한꺼번에 하는 방법이
선미를 바깥으로 던지는 것이다 — 선체가 진행 방향보다 안쪽을 향한 채 옆으로
미끄러진다. 이 슬립각을 안 그리면 배가 레일 위 기차처럼 보이고 경정으로
읽히지 않는다.

슬립각은 물리로 계산한다:

```
깎아야 할 비율 = (진입속도 − 선회속도) / 선회속도
슬립각 β = BETA_MAX × min(깎아야 할 비율 / DRIFT_REF, 1)
```

**안쪽을 파고든 배일수록 선회 속도가 낮아 더 많이 깎아야 하므로 더 크게
밀린다** — 인빠지기가 화려해 보이는 이유이고, 부표를 20m 로 감는 최내측이 23.0°,
35m 로 크게 도는 최외측이 10.8° 로 나온다. 화면에서는 선회 중간이 최대가 되도록 sin 으로
펴서 그린다(진입에서 던지고 정점에서 최대, 탈출에서 되잡는 실제 순서).

서버는 좌표를 넘기지 않는다. 배마다 **구간 경계에서의 시각·가로 오프셋·슬립각**
만 주고(6척 × 14경계, 약 2.4KB) 코스 기하는 브라우저가 계산한다.

### 무엇을 주장하고 무엇을 주장하지 않나

* **주장한다**: 1턴마크 선두 확률, 최내측 확보 확률, 전법 분포, 전개 대본.
* **주장하지 않는다**: 승률. 순위도 확률도 학습된 모델이 정한다. 화면에
  확률이 두 개 나오면(모델 63.8% vs 시뮬 88.8%) 읽는 사람은 둘 다 믿지
  않는다. 그래서 시뮬레이션의 자체 승률은 화면에서 뺐다.
* **대본은 '예상대로 흘러간 판'을 고른다.** 예상판이 A 를 1순위로 적어 놓고
  전개에서 B 가 이기면 페이지가 스스로를 반박한다. 결과를 지어내는 것이
  아니라, 같은 물리로 계산한 1,500판 중 예상이 실현된 판을 골라 보이고
  화면에 그렇게 밝힌다. 그 배가 한 번도 못 이기면 억지로 만들지 않는다. 시뮬레이션의 초 단위
  숫자도 믿을 수 없다 — 수면 제원과 횡가속 한계가 추정값이다. 믿을 수 있는 것은
  순서와 방향이다.

공개(v1) 예상은 전개까지 **함께 확정 저장**한다. 결과를 본 뒤에 다시 돌린 전개는
아무것도 증명하지 못한다.

## 실전 베팅 전략 — 결론

`python -m boatai.strategy` / `/strategy/` 페이지.

**베팅금 조절로는 안 된다.** 기대값은 `Σ 베팅금ᵢ × (배당ᵢ×적중ᵢ − 1)` 이고,
베팅금은 각 항에 곱해지는 양수일 뿐이라 개별 베팅이 음수면 합도 음수다.
마틴게일은 수익률을 못 바꾸고 **파산을 앞당긴다** — 매 경주 단승에서 정액은
977번째에 자금이 말랐지만 마틴게일은 **167번째**에 끝났다.

게다가 경정은 **1회 구매 한도가 10만원**이라 회수 베팅 자체가 성립하지 않는다.
1만원에서 두 배씩 올리면 8만원이 한계이고 그다음(16만원)은 살 수 없다.
즉 4연패를 넘어서면 회수 수단이 사라지고 그때까지의 손실(15만원)은 그대로
확정된다. 매 경주 단승 표본에서 그 구간을 넘어선 연패가 **282회** 있었다.
시뮬레이터는 이 한도를 그대로 적용한다(`MAX_STAKE`).

**바꿀 수 있는 건 선택이다.** 승식과 경주를 고르면 회수율이 오른다:

| | 회수율 |
|---|---|
| 모든 조합 매수 (=환급률) | 70.3% |
| 매 경주 단승 | 86.4% |
| 연승 + 1순위 승률 55%↑ + 1코스 | **96.9%** (검증기간 96.0%) |

**그래도 100%를 넘지 못한다.** 규칙을 격자로 훑어 2022년 이전에서 고르고
2023년 이후로 검증했는데, **탐색 기간에서조차 100%를 넘은 규칙이 0개**였다.

남은 3%p 를 넘으려면 기대값(확률 × 배당)을 계산해야 하는데, **경정 공개 API 는
발주 전 배당을 주지 않는다.** 계산할 수 없는 것은 고를 수도 없다. 그래서
이 저장소는 "덜 잃는 것"까지만 하고 멈춘다.

## 정직성 장치

경마 버전에서 실제로 겪은 사고들을 그대로 막아 두었다.

* **예상 확정 저장** — 발주 시각이 지난 경주의 예상은 다시 쓰지 않는다. 발주 시각을
  모르는 경주는 아예 예측하지 않는다(발주 전에 만들었다고 주장할 근거가 없으므로).
* **실전 / 모의 분리** — `predict upcoming` 은 `v1`, `predict backfill` 은
  `v1-oos` 로 남긴다. 사후에 만든 기록을 실전 적중률에 섞지 않는다.
* **배당 없는 경주는 판정하지 않는다** — 배당표에는 적중 조합만 저장된다.
  자료가 안 들어온 경주를 '불발'로 세면 맞힌 경주가 실패로 남는다.
* **빈 값으로 덮어쓰지 않는다** — 발주시각은 출주표에만, 경주일자는 착순에만
  있다. 나중 수집이 앞선 수집을 지우지 않도록 upsert 가 `COALESCE` 로 병합한다.
* **결손을 센다** — `audit` 이 배당·착순·출주표·예측 누락을 세고 `--strict` 면
  비정상 종료한다. 성공한 파이프라인이 조용한 것은 신호가 아니다.
* **누수 테스트** — 결과에서 온 값이 피처 목록에 들어가면 테스트가 깨진다.

## 남은 것

* **틸트각 API 활용신청** — 효과가 가장 클 미승인 자료. 단, 발주 전에 공개되는지
  프로브로 먼저 확인해야 한다(발주 후면 학습에는 써도 예측에는 못 쓴다).
* **실전 기록 축적** — 지금 표는 전부 사후 워크포워드(`v1-oos`)다. `v1` 기록이
  쌓이면 그쪽이 진짜 성적이다.
* **회수율 개선** — 적중률이 아니라 기대값으로 고르는 방식(배당 예측 모델,
  선택적 베팅)이 없으면 공제율을 넘기 어렵다.
